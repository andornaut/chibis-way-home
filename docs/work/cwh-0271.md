## Scope

Reduce production art file count and encoded bytes through packing, compression or equivalent
formats. Compare the shipped outputs from matched builds. Preserve artwork, frame semantics,
device rendering, and the existing gallery and offline behaviour.

## Criteria

- The production build ships fewer art files and fewer art bytes.
- Report the before and after file counts and bytes, including any added metadata or duplicated
  files associated with the reduction.
- Verify that the changed assets render correctly, remain accessible in the gallery where
  applicable, and retain their existing offline availability.

## Outcome

- Stage previews: one 7,904-byte lossless atlas page replaces 21 PNGs totalling 18,703 bytes.
  All frames retain their pixels, the original five atlas pages are unchanged, and the build
  emits no duplicate preview PNGs. The matched builds went from 73 to 53 files,
  2,425,191 to 2,412,533 raw bytes and 61 to 41 precache entries. Those totals include offline
  metadata dropping from 18,990 to 15,103 bytes and other output growing by 2,028 bytes.
- Crash screen: the 564-byte standalone PNG preserves the exact pixels of the crash frame
  from the 5,532-byte sheet. The sheet remains an authoring and atlas source. The build
  emits only the crop as a standalone crash resource and leaves all six atlas pages unchanged.
  A separate matched build comparison kept 53 files and reduced raw output from 2,413,345 to
  2,408,122 bytes.
- Secure Chromium checks on the deployed asset bytes confirmed one 168x84 stage preview
  offline and an offline recovery screen showing the 48x42 crash image at 96x84 CSS pixels.
  The recovery check used a synthetic diagnostic. Gallery source art is unchanged and the
  production build omits the gallery.
