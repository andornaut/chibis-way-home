# Tech Plan

## Platform and delivery

- **Stack:** Phaser 4, TypeScript and Vite.
- **Hosting:** Cloudflare Workers static assets, no Worker script (`wrangler.jsonc`).
- **Targets:** landscape phone browsers with on-screen touch controls, and desktop browsers with a keyboard.
- **Tooling:** Node 24, Vitest, ESLint with the shared house rules, Prettier, markdownlint, husky + lint-staged, Dependabot, and the Test and AI attributions workflows.

## Architecture

- **Atlas:** a production build packs every PNG `public/art/manifest.json` lists (sprites, fonts, tilesets and backdrops) whole into atlas pages, each image's edge pixels repeated 1 px around it, written as lossless WebP with every pixel kept (the kit's `art/webp`) under `/assets/art/` with a content hash in the name (`src/tools/atlas/`); the atlas manifest that maps each art key and frame to its page and rect is built into the game's code. `BootScene` loads the pages and gives each key a texture that shares its page's source (`src/scenes/atlasArt.ts`), so the page uploads to the GPU once, batches draw from one texture, and code that names a key and its frames works as with the key's own files; each font is made from its `.fnt` and its frame there. Standalone manifest images load separately in both modes. The dev server has no atlas and loads each file on its own. Art's files stay as art writes them.
- **Back:** the kit's `pwa/backNavigation`, set up in `src/pwa/index.ts`, catches back, in a browser tab and the installed app, with a CloseWatcher where the browser has one and otherwise a guard history entry pushed from the player's first key or tap, and dispatches `back-pressed` on window for `PauseScene` and `StartScene`. Firefox for Android's installed app keeps the browser's own back.
- **Behaviour patterns:** `src/data/behaviours.ts` composes reusable state graphs for animals and moving props. A character selects a plan and an instance can replace it with a complete plan. Data names states, animation tags, move or wait primitives, entry heading capture and ordered transition conditions; the executor in `src/rules/behaviour.ts` handles either axis without character-specific sequencing. The antagonist and park boat use the same executor. Spatial values resolve from tiles to pixels when the zone loads, while durations remain seconds. Collision and interaction stay separate. Scene-associated patterns await their physical zone introduction; already-seen introductions activate them directly. Attempts reset movement and pattern state.
- **Crash screen:** `src/main.ts` first imports `src/crash/install.ts`, which installs the kit's crash screen in art's palette with the words in `src/data/text.ts`; it pauses the game on the first uncaught error. `?dev=1` adds the error's details. The build label's version and commit come from Vite's `define` in `vite.config.ts`, the commit reading `dev` without git.
- **Death:** a failed attempt freezes the world and camera while the bird recoils, falls onto frozen support, squashes on impact and makes a small upward bounce into a seated rest. Void falls use a visible fallback inside the frozen viewport. The required `DeathScene` card holds indefinitely, showing the zone and numbered stage names, current-attempt progress, last-attempt time, total active time in this run, historical successful-attempt best and attempt count. Back to title preserves progress and history; Try again is the safe default and retries the same layout in the same run with fresh object motion. Outside taps, back and Escape cannot close the card. Held input is cleared across transitions, and pause controls stay inert. A two-pixel themed progress strip tracks the current attempt, including backward movement. Death presentation and modal time do not add to active stage time.
- **Dialogue:** an unseen destination introduction opens at the beginning of stage one. `ZoneIntroductionScene` draws its data-selected antagonist outside the physical object list, holds the world through a manual conversation, then runs the actor offscreen before resuming. Its entry profile selects the character, animation tags, spawn offset and escape speed; cinematic art has no contact body, projectiles or encounter quota. Completing or skipping the conversation remembers the introduction per destination for the playthrough, so retries and replays omit it. Ordinary conversations use `DialogueScene`, with plans and speakers in `src/data/dialogues.ts`, paragraph text in `TEXT.lines`, and names and controls in `TEXT.dialogue`. The fixed top panel shows one paragraph, at most three measured lines at the shared font size. Each speaker names a portrait side: the bird remains left and other speakers right; images are repositioned without mirroring. Secondary Skip and primary Continue share a footer below the panel. Fresh taps or non-repeating keys advance; Tab and arrows focus actions, and Enter or Space activates a focused action. Held touches and drags do not advance. Skip and the final paragraph open a required terminal choice when the plan defines one, otherwise end the conversation. `DialogueChoiceScene` uses the shared card and buttons, starts without a focused answer and cannot close through Skip, back, Escape or an outside tap. The zone remains held through the choice; only a selected option id is returned, with no actions or flags applied. All dialogue input is consumed. The dialogue stops before notifying its opener once through `dialogueClosed(selection?)`.
- **Entity mechanisms:** code defines mechanisms; typed data selects entity profiles, traits and tuning without dispatching on entity ids. Existing motion profiles map `ease` to the kit's `sineInOut` easing and other travelling profiles to `linear`; hop lift, phase and lazy seeded leg generation remain local. Reusable pure mechanisms belong in the shared kit when both games have compatible consumers. Changes preserve seeded randomness and replay.
- **Game data:** `src/data/types.ts` holds the shapes; every other file in `src/data/` holds gameplay's values, with the words the player reads in `text.ts`.
- **Installed app:** the home page's Install button (`src/homePage/main.ts`, on the kit's install flow) and the settings card's Install row (`src/pwa/installOffer.ts`) show the browser's install prompt, or the steps for a browser that installs only from its own menu (iOS, Firefox for Android), and hide once installed. The web app manifest starts the app on `/play/`, which the service worker precaches, full screen and locked to landscape. In the app the game page has no nav bar, so no link leaves the game. The screen stays on during play, and sleeps as usual while the pause card is open or the page is hidden; the installed app asks the browser once per launch to keep its storage.
- **Play view:** the canvas fills `#game` (Phaser's `Scale.EXPAND`), stretched by the most the base resolution takes on both axes, so where `#game` is wider or taller than 2:1 the canvas is too. Each scene's camera shows the game's base-resolution view at the canvas's top, centred across (`src/layout/playView.ts`, `src/scenes/playCamera.ts`), and the canvas's own bars, in the page's ink, fill the rest. Every control stays inside the view across, its drawn edge at least `CONTROL_EDGE` (8) from the edge it is placed against (`src/layout/playView.ts`): the pause button 8 in from the view's top and left; Jump 8 in from the view's right and `CONTROL_BOTTOM` (20) up from the canvas's bottom, with Use 100 above it and 85 in from the view's right, and the move hint level with Jump, as far in from the view's left as Use is from its right; so the bottom controls move into a bar below the game, and none into a bar beside it; the zone draws them in a second camera over the whole canvas, as the pause scene draws the pause button and the dim, and reads a touch's button through the same shift. The move hint (`src/view/moveHint.ts`) is a drawing with no press area: at rest it sits level with Jump, as far in from the view's left as Use is from its right; while a drag moves him, its ring sits where the drag began, held left or right the way he moves, with its knob up to 12 pixels left or right of the ring's centre the way the drag goes, and it returns to rest on release. The kit's `followFrameTurn` keeps the page no taller than the visible area (the visual viewport, not viewport units, which an installed app can size past the screen) and refits until the sizes settle on every signal that the visible area or the frame's turn may have changed, with a check four times a second while the page is visible for a fit or turn gone stale with no signal.
- **Press areas:** every button's press area is its drawn button grown on every side by a quarter of its shorter side, between 6 and 16 base pixels, and to at least 48 square about its centre (`HIT_RULE` in `src/layout/hitAreas.ts`). Use and Jump instead press within 100 of each centre: a clear circle of radius 63 (`TOUCH_CIRCLE_RADIUS`) and the move hint's radius of 37 beyond it, so a drag, which starts only off the buttons, draws the hint clear of each clear circle. The two are cut along the line midway between their centres, so they meet and never overlap, and Jump's reaches on into the screen's bottom-right corner, from its centre. Where two areas overlap, the button whose centre is nearer the press wins (`pressedArea`).
- **Stage completion:** `src/rules/stageCompletion.ts` derives the route from each destination's ordered catalogue. Completing a nonfinal stage saves completion and opens the cleared stage's screenshot and run statistics with Continue, which starts the next stage directly. Back, outside taps and held input do not bypass the interstitial. Completing a destination's final stage shows its outgoing exchange, then the cleared-stage screenshot and stage statistics beside the actual zone-visit aggregate, before opening the map for automatic travel; the final catalogue stage retains its celebration. Interstitial time does not count as active stage time.
- **Stage element roles:** themes bind shared element roles through `ThemePlan.bindings`. Assembly uses one `bindElement` overlay for repeated backgrounds, local scenery, chunk objects and filled doors. An explicit role without a binding is an error; untagged legacy instances retain their configuration. Bindings select the character and may replace behaviour, lines, parallax, phase or visual skin, merge tuning overrides and set or explicitly clear an introductory scene with `scene: null`. Template placement, dimensions, flags and rooms remain unchanged. `ThemePlan.door` names a required binding role; filled doors use its selected character's dimensions to centre across their slot and stand on its floor. Chunk bounds and seam checks resolve each theme's bindings.
- **Visual skins:** `skin: {art, tileset}` changes presentation while the selected character remains the source of collision, dimensions, hitbox, motion and interaction. A tileset key selects tile art; `null` explicitly selects sprite/image art without falling back to the area's tileset. Sprite art retains its bottom-centred anchor. Collidable skins must preserve the canonical effective hitbox; declared sprite hitboxes are compared after anchoring, tile pieces must match the physical footprint, and skin tiles must exist at the correct tile size. An explicit character change through a binding is configuration, independently of a visual skin.
- **Zones:** a zone is played from its `ZonePlan` in tiles (`src/data/types.ts`), converted once to pixels for the rules: areas of terrain and placed instances. Each instance is a character (`src/data/characters.ts`: its art, animations by state, size, words and quirks) on an archetype (`src/data/archetypes.ts`: its collision and default motion, reaction and interaction), resolved once at load into a flat object, an instance's overrides over its character's tuning over its archetype; carried-choice flags place or leave out an instance. Use at a door shows its room (Rooms). Use reaches a door wherever his drawn frame (art's bird frame, placed over his collision box as the zone draws it) intersects the door's rect at all, which is its drawn rect; of two doors under his frame, the one whose centre is nearest his opens (`doorAt` in `src/rules/zone.ts`). His collision box crossing an area's linked edge automatically enters its named target entry, at any height. An unlinked right edge clears the stage, which fades to black and follows its catalogue completion route; the zone walk follows the same links and never presses Use. His box reaching an unlinked left edge (left of `backX`, the first column's right edge) ends the zone without clearing it (`turnedBack`): it fades to black the same way and opens the map with him on that zone, nothing completed and the save unchanged; through `?zone=` it plays the same zone again. Every zone's start, hand-built and every recipe's, sits clear of the first column, and held left from it he reaches that column, nothing in it stopping him (`src/data/zones.test.ts`), and the zone walk counts a try that takes him into it as failed, so neither ends a zone by turning back. A held key's repeats never press it, so a key held from before the zone resumes counts only once pressed again. A zone in `RECIPES` (`src/data/zones.ts`) is assembled from the chunks and themes in `src/data/chunks.ts` for a seed drawn afresh each time he enters it (`src/rules/assemble.ts`): its start chunk, a seeded run of its theme's chunks whose seams join, within its inclusive difficulty band regardless of position, each at most its `maxPerZone` and never one twice in a row, then its finish chunk, the whole within its length, searched with backtracking, with its events and doors in seeded slots (recorded in the plan): a filled door slot places the theme's door at its own size, centred across the slot (half a tile in where the widths differ by an odd count) and standing on its floor, leading to its room. Events are not built yet. Each chunk's contents move to its zone columns, its terrain looks map to the theme's tileset, and the theme's repeated backdrops span the zone; the result is an ordinary `ZonePlan`. The tests check every chunk against the chunk and seam rules, validate each recipe, and walk each chunk alone (`src/data/chunks.test.ts`, `src/sim/chunkWalk.test.ts`), on small fixtures in `src/testing/chunks.ts` as well as gameplay's chunks. A zone's start is its only checkpoint, and each restart is a new attempt that rolls the objects' random motion afresh from the zone's seed (`?seed=<n>` fixes it).
- **Ordered stages:** each section declares its whole-column `length` range, including only its applicable global stage caps. One or more weighted compatible middle chunks fill that range; limited chunk counts and nonidentical neighbours apply across the stage. Optional `difficultyWeights` multiply chunk weights by grade in flat and ordered recipes; omitted grades keep weight 1 and zero excludes a grade. `areaOrder` retains the generated section sequence and each area's `walkLinks` names its automatic left and right stair destinations. Section changes redraw local art and camera bounds, reset held controls and animation pose, and retain the stage clock and attempt. A retry starts at the stage checkpoint. `src/rules/stageProgress.ts` supplies the same current-attempt fraction to the HUD, death card and diagnostics: ordered sections contribute their playable widths, and the bird's centre supplies local progress. Diagnostic cold starts retain the original stage's progress origin while selecting their own retry checkpoint. Bot input and stall detection reset local state at each section change without reseeding decisions or extending tick and trace budgets. Explicit diagnostic goals remain area-local, including a goal crossed immediately before a stair transition.
- **Offline play:** the build writes `/sw.js` (the kit's service worker with `src/pwa/cachePolicy.ts`), precaching `/play/`, what it loads and links, the atlas pages, and the manifest, data, font and tileset descriptions under `/art/`. `src/pwa/` registers it in production: at once on a page a version controls, and on a first visit once the zone shows, so the precache does not compete with the game's own downloads (`registerWhenDue`). A new version's install copies the hashed files the last one stored and fetches the rest. The game loads while a fresh load checks for a newer version; `BootScene` holds only the zone for it (`launchReady`, up to 4 seconds). A newer version takes over before the player interacts (a tap while the game loads counts), and after that the page's "Update available" toast offers it while the zone is in front, never under the pause card or a room. It checks on each load and whenever the page comes back into view, at most once a minute. The icons `src/pwa/icons.ts` lists (the web app manifest's, and the pages' favicons and apple-touch-icon) are written again under content-hashed names under `/assets/` (`/assets/icons/`, and `/assets/art/` for the favicons), which the pages, the manifest and the precache name (the kit's `hashedIconsPlugin`), so a redrawn icon reaches an installed app and the hashed build output's year of caching covers them; `/manifest.webmanifest` keeps its name and is fetched network-first.
- **Map screen:** six themed destinations each group an ordered catalogue of stage-node ids. The overview shows every regional miniature and name; locked markers use padlocks and unbuilt markers use question marks. Unbuilt stages have no playable plan and cannot be entered. Only manually pressing Continue opens `StageSelectScene`. Its catalogue-ordered cards show actual stage screenshots, standard-size names and smaller stage-number labels. The latest unlocked stage uses the primary style; locked later stages remain visible, grey and disabled. Earlier stages remain replayable. Closing, back, Escape and outside taps return to the map without selecting a stage. A new navigation press must focus an answer before keyboard activation, so opening input never selects one. Completed stage ids preserve unlocks across replay, and only the configured final apartment stage triggers celebration. The progress format retains catalogue stage ids as additional stages are built. Back to title remains secondary on the left; Continue remains primary on the right and the default map action. Tab selects footer actions, while Left/Right and A/D select unlocked destinations. Returning to the title preserves progress. After a destination's second stage clears, including a replay, the map animates the bird along the drawn route to the next built destination. Input remains locked during travel, the saved position changes on arrival, and arrival does not launch a stage. The final stage retains its celebration.
- **Modal cards:** pause, settings and install steps, restart, stage selection, required dialogue choices, death, updates and paused physical dialogue share the kit's modal input gate and palette-remapped backdrop. Each scene adapter owns its cameras and dismissal: modal visuals remain hidden until readback completes, with an opaque ink fallback when capture is unavailable. Owned snapshots and late captures are cleaned up on shutdown; Death preserves its already-dimmed frozen source, and Settings reuses Pause's cached touch-setting views. The top modal alone accepts Phaser pointers, keyboard, forwarded keys, back events and native page controls. Every stack change clears held controls and invalidates pending presses, so a release cannot cross into a newly opened card or the world. Outside taps dismiss only closeable cards; required cards remain open. Cards use measured content layout (`src/layout/contentCard.ts`), art's pale `ui-settings-card`, whole-card-centred titles and top-right close faces inset 6px, with full 48px targets excluded from title and body controls. Buttons share one shape, with the primary first. Rooms, cutscenes, zone departure and celebration remain full screens.
- **Parallax:** decorative backdrops can set `parallax: { x, y }` on an instance or a theme backdrop, each factor from 0 (fixed in the view) to 1 (world speed), with both axes at 1 when omitted. Assembly preserves these factors and `ZoneScene` applies them as camera scroll factors while leaving the objects at their world positions. Repeated backdrops keep their full run width, so a layer spanning the zone still covers the view at either horizontal camera limit. Placed scenery retains its own art height and bottom anchor while the camera climbs. Collision, interaction, moving objects and non-backdrop art cannot use non-default factors.
- **Modal layout:** pause, settings, install steps, restart, dialogue choices and stage selection measure their text and actions through `src/layout/contentCard.ts`. Cards use the shared kit minimum width (half the full logical viewport, bounded by the available view) and 16px outer padding, 16px text lines, 4px stacked-row gaps and 8px between content groups. Action buttons remain 48px high and share the widest label width plus 32px within each group. Titles reserve symmetric clearance from the full close target and stay centred. If no full-width death card can clear the seated body, its safe available rectangle excludes the body and its clearance before applying the same maximum-width clamp. Close faces remain 24px with an unclamped 48px target. Body text and interactive targets start at least 8px below that target; font scale stays fixed.
- **Pause card:** `PauseScene` runs beside `ZoneScene` and draws over it: the pause button at the view's top-left corner, and the card (`src/layout/pauseCard.ts`) that it, P, Escape and back open, with three content-sized buttons sharing the standard height and group spacing, their labels centred: Resume, the primary, then Settings and Back to title. A change of the page frame's turn while the zone plays (the kit's `onChange`) opens it too. The card pauses the zone over a dim of it read back from the canvas and redrawn two steps down each colour's ramp (palette.json's `dim2`, `src/view/dim.ts`), read once for each mix of the two touch settings shown and hidden so the settings card's Move controls and Action buttons rows update the view behind it. Resume, the close X, P, Escape, back and a tap outside it close it; Back to title ends the zone for the start screen. Tab and the arrows move art's focus ring through Resume, Settings, Back to title and the close X, and Enter and Space press the focused one. While the zone is not in play (under the card, and while `BootScene` loads) the game draws on every Nth display frame, about 60 a second, each draw advancing by the skipped frames' time (the kit's `clock/phaser/capFrameRate`); in play it draws every display frame.
- **Phaser boundary:** only `src/scenes/` and `src/main.ts` import Phaser or a scene, enforced by ESLint's `no-restricted-imports`. Logic, layout and data are Phaser-free, so they unit-test without a renderer.
- **Phaser build:** the game runs on WebGL alone, with no sound. A production build bundles Phaser from its source without the namespaces the game does not use, the Canvas renderer or the sound manager (`PHASER_BUILD` in `src/tools/phaserBuild.ts`, built by the kit's `build/vite/phaserBuildPlugin`; its test fails when the game uses something it leaves out), in its own hashed chunk, so an update that changes only game code keeps Phaser's file. The dev server and Vitest load the package's own bundle.
- **Portrait:** on a touch screen in portrait, the kit's turned page frame (`view/frameTurn.ts`, `view/frameTurnLandscapeGame.css`, imported by `src/main.ts`) turns the game page's frame (the nav column and the game) onto its side to fill the screen, and moves the safe-area insets onto the frame's turned edges as `--inset-*`. It turns 90 degrees clockwise, read with the phone turned counter-clockwise, or -90 where the screen reports portrait-secondary (upside down). `src/input/frameTurn.ts` watches the turn. Touches map through it (the kit's `pageToGame`), and the kit's `followFrameTurn` has Phaser measure `#game`'s own size, leave the canvas's placement to `src/main.css` and map its pointers the same way. When the browser turns to landscape, the frame is unturned.
- **Rooms:** a door is an instance whose archetype is `door`, with a `room` from `ROOMS` (`src/data/rooms.ts`); the resolver refuses a door without a room and a room on anything else. Use at it holds the zone still and plays the door's `open` tag (its character's `animations.open`, else the tag named `open`) where its art has one, for as long as the tag runs (`src/view/doorOpen.ts`); then `ZoneScene` launches `RoomScene` and pauses, so the pause button hides and P, Escape, back and a frame turn leave the pause card shut. `RoomScene` hides the zone and fills the whole canvas with ink: the room's backdrop, or a PLACEHOLDER frame, its animations and cast, its name centred, and Leave at the view's top right (`src/layout/roomScreen.ts`), art's `ui-button` with `ui-focus` round it under keyboard focus. Leave, back and Escape close it (`src/pause/roomInput.ts`); Tab and the arrows focus Leave, and Enter and Space press it. The zone resumes with him at the door as he was, the door closed again (its idle tag), with no key or touch held. A room changes no save, so reopening the game mid-room opens the start screen; Continue opens the map with him on that zone. A room's `enter` and `shop` are typed but not built.
- **Save data:** progress uses the kit's versioned save in `localStorage` under `chibis-way-home.save`. It stores completed stage-node ids, the selected stage and seen physical zone introductions, and loads after `launchReady` before the first screen appears. Invalid, incompatible or older progress is backed up under `chibis-way-home.save-backup` and resets; a future version is left alone. Before version 1.0, format or id changes bump the save version and reset older data without migration. Every normal cold launch opens the start screen. Saved progress offers Continue and Restart; manually choosing Continue opens the map. Restart confirms first, then clears only progress. The separate version-4 `chibis-way-home.stats` save retains historical records across progress restarts. Fresh stage entry starts a new run with one attempt; death retry resets only the attempt clock and increments its count, retaining the run total. Stage records use the fastest successful attempt. An actual zone visit aggregates only its own stage runs and reports missing stages as partial; a zone record requires every catalogue stage in that visit and uses the sum of its successful attempt times. Physics steps accumulate in memory, with one-second checkpoints and immediate flushes on pause, death, exit and page lifecycle events. Menus, introductions including their cinematic escape, paused dialogue, cutscenes, death presentation and retry-card time do not count. Where storage is unavailable, saves last only for the page session. Settings keep their own keys. Developer `?zone=` routes bypass the progress save; unknown diagnostic stages do not record real-stage stats.
- **Loading:** the initial HTML and lightweight entry show the same two-pixel themed strip as gameplay through shared kit geometry and DOM/Phaser adapters. Boot reports completed-file progress; startup checks, stage preparation and service-worker installation remain indeterminate. Stage entry yields a paint before synchronous assembly, keeps input and updates disabled, and releases the strip after the first prepared frame. Background caching does not delay play; its indicator follows the shared offline-activity callback without changing registration timing. Preview capture suppresses loading UI.

- **Scenes:** `BootScene` runs first: it loads everything `public/art/manifest.json` lists and makes an animation of each sprite tag, keyed `<sprite>:<tag>`, with the tag's frames and durations from the sprite's Aseprite export. A tag the sprite's manifest entry lists in `once` plays once and holds its last frame; every other tag loops.
- **Security headers:** the build writes `dist/_headers` from `src/headers/securityPolicy.ts`: a Content-Security-Policy per page with its inline blocks hashed, and a year's caching for hashed build output under `/assets/`.
- **Settings card:** the pause card's Settings row opens `SettingsScene` in the pause card's place over the same dim, and the start screen's Settings button over the start screen (`src/layout/settingsCard.ts`): the Move controls and Action buttons rows, the Install row while the game can be installed, and the build label. The scene that opens it passes it the keys and back, and gets it back when it closes. Install shows the browser's install prompt, or the install steps card in the settings card's place. The close X, P, Escape and back close the card on top, back to the scene that opened it; Tab and the arrows move the keyboard's focus and Enter and Space press. Each setting is kept in `localStorage` under its own key (`src/settings/touchControls.ts`). Move controls shows the move hint and Action buttons shows Use and Jump, both on by default; hiding either hides only its drawing, and movement and the button presses still work. A player who hid the old single Touch controls setting starts with both hidden.
- **Shared kit:** `@andornaut/game-kit` is a committed copy at `vendor/game-kit/`, synced by game-kit's `scripts/sync-into.sh` with its source commit in `vendor/game-kit/KIT_COMMIT`, and changed only at its source.
- **Start screen:** The logo uses its loaded frame dimensions and scales proportionally into the space between the nav bar and the unchanged action row. The home page reserves the image's intrinsic height without a fixed brand aspect ratio. Start and Continue use the shared dslate primary face with white text, without a play mark; Restart uses the grey secondary face. With a save, Restart sits on the left and Continue on the right; Continue remains the default keyboard action and first focus target. Their buttons share standard 48px height and matching widths, with an 8px gap when paired. The game always opens on `StartScene` (`src/layout/startScreen.ts`) after loading and startup readiness checks, including with saved progress (Save data): Start opens the map with him on the first zone; once progress is saved, Continue (in Start's row, beside Restart) opens the map where he stands (Save data), under a nav bar with Settings, which opens the settings card, and Exit at its right end. Behind them is zone 1's street, dimmed two steps down each colour's ramp as the pause card dims the zone: `ZoneScene` draws it once as a paused, input-free backdrop without the bird or the touch buttons, the start screen reads that frame back from the canvas, and the dimmed texture is kept for later visits. Exit, and back with no card open, leave through the kit's `exitApp`: an installed app closes its window, and a browser tab goes to the site's home page. Back with the settings card or its install steps open closes them. An installed app whose window a script cannot close (the kit's `appCannotClose`, read in `src/pwa/index.ts` as the page loads: every app but Chrome's on Android and Chrome's and Edge's on desktop, or one whose history holds more than the game's entry) shows no Exit, Settings takes the right end, and back there is the browser's own. Tab and the arrows move art's focus ring through Start, Settings and Exit, as on the pause, settings and install steps cards, and Enter and Space press the focused one (Start with nothing focused).
- **Test helpers:** `src/testing/` is importable only from tests.
- **View:** `src/view/` picks each sprite's tag and whole-pixel position from the game state, Phaser-free, so the scenes only draw what it picks.

## Bounded simulations

`npm run simulate -- --help` describes the headless stage runner. Run it only inside the project container. For a small diagnostic run, use `npm run simulate -- --stage street --seed 1 --runs 1 --max-steps 600 --max-retries 0`. Larger batches require coordination with gameplay; this command is not a routine gate.

`src/sim/simulate.ts` exposes `prepareStage(layout)` and `simulateStage(tuning, prepared, config)`. `src/sim/report.ts` batches explicit seeds through a caller-supplied preparation function. Layouts and static sensor indices can be reused between policies. The CLI loads art metadata once, assembles each seeded stage once and performs no rendering or reachability search. Its Node-only asset loader is separate from the pure engine and frontend.

Rollouts call the real `stepZone` at `STEP_SECONDS`, including collision, moving platforms, behaviour patterns and explicit retries. Conversations are acknowledged at the runtime proximity and activate their actors; presentation, menu and retry-card waits consume no active time. The bot does not use doors or make narrative choices. Retry retains the assembled layout and uses the real attempt reseeding. Tick and retry limits bound each run and report exhaustion explicitly.

JSON output includes current-attempt and peak progress, completion, death reasons, retries, active seconds, steps and runtime. Per-run timing measures rollout only; aggregate timing includes stage preparation, and total CLI timing also includes asset loading. Timings vary by machine; deterministic gameplay metrics exclude timing. Active seconds count physics ticks across all attempts. Progress uses the same weighted current-position calculation as gameplay across ordered areas. Coverage lists only visited areas and chunks, plus automatic area transitions; prepared but unvisited floors are not covered. `lastAttemptSeconds` reports only the final executed attempt; `successfulAttemptSeconds` appears only after a stage clear and excludes earlier failed attempts. Prediction steps never count toward active time.

Optional `stopAfterStallTicks` (`--stall-limit`) ends a policy with no further directional progress as `policy-stall`, independently of tracing and its event cap. Area changes and retries reset that progress window. Allow for moving-platform cycles and inspect final movement, waiting ticks and planner status before interpreting a stop. Optional `maxWallTimeMs` (`--max-wall-ms`) bounds rollout wall time and reports `wall-budget`; the batch limit (`--batch-wall-ms`) also bounds preparation and dispatch, returning `omittedSeeds` for unstarted runs. Wall limits depend on machine speed and are incomplete diagnostics, not gameplay failures. Use an external container timeout to bound synchronous preparation and individual planning calls as well.

Optional `start` selects an existing `{area, entry}` or a collision-box top-left `{area, x, y}`. Bounds and overlaps are checked against actual terrain and initial live objects. Sections initialize the real area's actors and motion at time zero; they are cold starts, not snapshots of earlier play, and retry returns to that same section. No preceding tutorial completion is inferred.

Optional `goal: {area, x}` stops a section at its configured leading-edge threshold in the movement direction with `goal-reached`, independently of stage `cleared`. Goals must be in bounds and ahead of the start. A death at that tick remains a failure. Without a goal the whole stage remains the target; section goals do not count as stage completions.

Optional `seeds` separates `layout`, `motion` and `bot`; each missing value falls back to the existing `seed`. Batch preparation receives the layout seed, rules receive the motion seed and the bot receives its own seed. Results include resolved seeds, the complete supplied configuration, actual starting position and caller-supplied `provenance.build` / `provenance.data` identifiers. Supply exact non-secret source identifiers when comparing data versions. The Node loader adds an SHA-256 identifier of the actual layout, assembled plan and tuning; the CLI also records the Git revision when available, with explicit `--build-id` and `--data-id` overrides. Git identifiers do not describe uncommitted code. Prepared catalogue stages reject mismatched layout seeds and cache only the most recent layout, bounding cache memory.

Optional `trace` requires `maxEvents` and `stallTicks`; `sampleEveryTicks` additionally samples position and input. The run-wide event cap bounds all attempts together and reports dropped events. Death events replace non-death samples when the cap fills. Each event records attempt/local tick, global tick, area, position, input, chunk index and assembly ID where prepared metadata supplies it, death reason and the nearest or overlapping collidable object's position and behaviour. Object attribution is a diagnostic candidate, including after swept contact, not proof of causation. With tracing omitted the runner creates no diagnostic events or object-attribution scans.

Bot inputs expose reaction ticks, look-ahead pixels, jump-hold ticks, error probability, movement direction and jump policy. The reactive policy probes local support, walls and hazards using indexed terrain and current moving-object positions. Optional `jump: "planned"` selects bounded navigation configured by `skill.navigation`: `horizonTicks`, `maxCandidates`, `replanTicks` and `maxPhysicsSteps` (CLI `--plan-horizon`, `--plan-candidates`, `--plan-replan` and `--plan-steps`). Planning uses the real engine; its counters report decisions, candidate rollouts, prediction physics steps and budget exhaustion. The prediction-step budget applies to the whole run, including retries and area transitions; exhaustion reports `prediction-budget` unless the executed tick already cleared the stage or ended in death. A planner with no safe candidate or an exhausted budget has not proved the layout impossible. It does not plan a route, schedule enemy phases or search for takeoffs. The supplied diagnostic settings are not calibrated human skill presets; gameplay owns calibration. Failure by this bot is not evidence that a stage is impossible. Diagnostic defaults enable adaptive holds between `minJumpHoldTicks` and `jumpHoldTicks` for low obstacles, retain longer holds for gaps and hazards, and release after reaching a measured obstacle top. These are local geometric estimates, not skipped physics. `waitForMovers` stops movement for a nearby missing moving landing, resumes on live alignment, and caps waiting with `maxWaitTicks`; no predicted platform position replaces real stepping. Legacy caller skill objects can omit these optional controls.
