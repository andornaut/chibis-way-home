# Tech Plan

## Platform and delivery

- **Stack:** Phaser 4, TypeScript and Vite.
- **Hosting:** Cloudflare Workers static assets, no Worker script (`wrangler.jsonc`).
- **Targets:** landscape phone browsers with on-screen touch controls, and desktop browsers with keyboard and mouse controls.
- **Tooling:** Node 24.21.0, Vitest, ESLint with the shared house rules, Prettier, markdownlint, husky + lint-staged, Dependabot, and the Test and AI attributions workflows.

## Site

Vite builds the HTML inputs in [`pages/`](../pages/) and serves the game at `/play/`, the home page at `/`, the gallery at `/art/` and tuning at `/tuning/`. [`vite.config.ts`](../vite.config.ts) uses the local [game configuration adapter](platform/build/vite/gameConfig.ts); native package exports resolve the pinned shared libraries without source aliases. Build and deployment commands are in the [root README](../README.md).

Tech owns implementation, integration and reviewed release approval. The monitor
owns bus operations after approval; the [deployment workflow](../README.md#deploying)
defines the handoff and scheduled checks.

## Architecture

Player-facing rules live in the [gameplay design](../gameplay/design.md); this section describes their implementation.

### Data-driven entities

- **Entity mechanisms:** code defines mechanisms; typed data selects entity profiles, traits and tuning without dispatching on entity ids. Existing motion profiles map `ease` to the kit's `sineInOut` easing and other travelling profiles to `linear`; hop lift, phase and lazy seeded leg generation remain local. Reusable pure mechanisms belong in the shared kit when both games have compatible consumers. Changes preserve seeded randomness and replay.
- **Behaviour patterns:** `src/data/behaviours.ts` composes reusable state graphs for animals and moving props. A character selects a plan and an instance can replace it with a complete plan. Data names states, animation tags, move or wait primitives, entry heading capture and ordered transition conditions; the executor handles either axis without character-specific sequencing. The antagonist and park boat use the same executor. Spatial values resolve from tiles to pixels when the zone loads, while durations remain seconds. Collision and interaction stay separate. Scene-associated patterns await their physical zone introduction; already-seen introductions activate them directly. Attempts reset movement and pattern state. Acquired actors with `idleWatchdog` retain displacement history across graph and escape changes, and attempt bounded, verified supported recovery only in eligible phases (`src/rules/behaviourIdle.ts`). Active tell phases draw a steady 2px red outline with a 1px outer ink border around the current animated frame’s alpha silhouette ([renderer](scenes/bossWarning.ts), [geometry](view/bossWarning.ts)), using `BOSS_WARNING` without changing body pixels or contact bounds. Chase, committed attacks and cooldown have no outline. Pursuing bosses acquire when their horizontal centres share an authored chunk or both body centres are in the current camera view. Line of sight and ground reach do not gate acquisition. Settled rearming uses the same awareness with its existing reach guards. Attack-specific `visible` checks still require both body centres inside the current camera view and a clear line through solid terrain and solid objects; ledges do not occlude. `src/rules/perception.ts` supplies the shared chunk and sight predicates.
- **Behaviour pipeline:** each tick runs perceive, decide and act for every behaviour-driven object. Perceive: `src/rules/zone.ts` builds one [`BehaviourPerception`](rules/behaviourPerception.ts) per object, holding Chibi's state and tuning and the behaviour world: present terrain, platforms, hazards and chunks, the camera view, the traversal frame with support and crumbling predictions, the targeted-attack window and an object-local `RandomStreams` factory named from the zone seed, attempt, area and object index. Decide: for each slice of the step, `decideSlice` in [`behaviour.ts`](rules/behaviour.ts) evaluates support ([`behaviourSupport.ts`](rules/behaviourSupport.ts)), escape settling, entry effects, the first matching transition, sampled intent and how long the decision holds, from the snapshot and the object's own layout and state only. Act: `actSlice` maps the decided motion to an ability kind and acts it through the explicit [ability table](rules/behaviourAbilities.ts): wait and supported dwell, track travel, target flight, supported landing, air chase, overhead swoop, ground chase and escape settling ([pursuit abilities](rules/behaviourPursuitAbilities.ts)). Abilities return the slice end, next state, carried support and traversal legs; graph checks reach them only through decision callbacks. Idle recovery and periodic repositioning are entries in a [recovery table](rules/behaviourRecoveryAbilities.ts), and the zone turns entry actions into force pulses and spawns through an [effect table](rules/behaviourEffects.ts). `stepBehaviour` perceives and advances in one call for fixtures. Game-independent mechanisms live in `src/ai/` without game imports: the ability interface, result and table, seeded stream factories and agent traces. Lint rejects `Math.random`, `Date` and `performance` under `src/ai/` and `src/rules/`. The `src/sim/behaviourTrace*.test.ts` suites hash a per-tick FNV-1a 64 trace of every behaviour-driven object, its transients and Chibi over every chunk's required walk, planned stage runs and the boss regression chunks against `src/sim/fixtures/behaviourTraces/`. Behaviour-level traces of every boss graph state and zone-level entry-effect traces cover attacks the zone scenarios do not reach (`src/rules/fixtures/`). `BEHAVIOUR_TRACE_DUMP=<dir>` writes full zone traces to diff against a dump from the base commit; `BEHAVIOUR_TRACE_UPDATE=1` re-records hashes for an intended behaviour change.

- **Boss simulator:** [`stepZoneBodies`](rules/zone.ts) is the physical part of the zone step: object frames with every behaviour object's perceive, decide and act, crumbling, forced transit, Chibi's body, contact and death; `stepZone` adds barks, doors, walk links and the stage exit. The game-independent [`simulate`](ai/simulation.ts) driver steps a model at a fixed clock with an injected controller and records a structured [agent trace](ai/agentTrace.ts) and its FNV-1a 64 hash. [`bossSimulator.ts`](sim/bossSimulator.ts) adapts it to bosses: it runs only `stepZoneBodies`, retries with every behaviour active after a death, ends when Chibi leaves the area and records each boss's state, motion, position, footing and support, pursuit phase, attack phase and cooldown, Chibi and the targeted-attack window per tick. Chibi is scripted or the seeded reactive bot. [Boss scenarios](testing/bossScenarios.ts) cover past regressions and each boss; [`bossSimulator.test.ts`](sim/bossSimulator.test.ts) proves the boss trace equals `stepZone`'s on every scenario and reproduces the recorded encounter trace hashes. [Boss properties](sim/bossProperties.ts) check the gameplay boss rules with thresholds read from behaviour data, through the generic [property checks](ai/agentProperties.ts); `bossProperties.test.ts` keeps the current behaviour's failures in an explicit known-failure list.
- **Traversal:** [behaviour traversal](rules/behaviourTraversal.ts) adapts actual current-frame terrain, moving platforms and hazards to the native game-kit planner. Unsupported or incomplete future geometry remains unknown. Preferred command prefixes share the original query’s work limits and terminal safety checks. Boss anticipation uses the actual preparation clock, keeping animation and silhouette contact on the same pose.

### Stage lifecycle

- **Opening:** `OpeningScene` plays the ordered beats in `src/data/opening.ts`, deriving motion from art's normalized recipe. Shot durations animate poses and transforms; each beat waits for fresh Continue, and Skip exits the entire sequence. New Game and confirmed Restart open it; saved Continue opens the map. Only completion or Skip acknowledges the dedicated progress marker, so interruption restarts at the first beat. Opening time does not start stage statistics.
- **Dialogue:** an unseen destination introduction opens at entry to the stage ID selected by `ZoneDialoguePlan.introStage`, or its first stage when omitted. Selectors outside the destination are rejected; earlier stages leave the introduction unseen. `ZoneIntroductionScene` draws its data-selected antagonist outside the physical object list, holds the world while the actor enters from beyond the current viewport, reaches its horizontal centre and speaks through a manual conversation. When the actor turns and starts running away, `introductionDepartureStarted` releases only the introduction-owned freeze and input scope; other pause or modal owners retain their hold. The separate, noncolliding actor continues offscreen before removal. Its entry profile selects the character, animation tags and shared approach/departure speed derived from the maximum charge speed; cinematic art has no contact body, projectiles or encounter quota. Completing or skipping the conversation remembers the introduction per destination for the playthrough, so retries and replays omit it. Ordinary conversations use `DialogueScene`, with plans and speakers in `src/data/dialogues.ts`, paragraph text in `TEXT.lines`, and names and controls in `TEXT.dialogue`. The fixed top panel shows one paragraph, at most three measured lines at the shared font size. Each speaker names a portrait side: the bird remains left and other speakers right; images are repositioned without mirroring. Secondary Skip and primary Continue share a footer below the panel. Fresh taps or non-repeating keys advance; Tab and arrows focus actions, and Enter or Space activates a focused action. Held touches and drags do not advance. Skip and the final paragraph open a required terminal choice when the plan defines one, otherwise end the conversation. `DialogueChoiceScene` uses the shared card and buttons, starts without a focused answer and cannot close through Skip, back, Escape or an outside tap. The zone remains held through the choice; only a selected option id is returned, with no actions or flags applied. All dialogue input is consumed. The dialogue stops before notifying its opener once through `dialogueClosed(selection?)`. A behaviour may declare one `spotted` speaker/line pair: the engine emits it once per placed encounter per attempt, retaining that record across area re-entry and clearing it on retry. `ZoneBarkScene` shows queued notices live for `BARK_DURATION_SECONDS`, without footer controls or a modal input scope. A fresh guarded panel tap dismisses only the current line and preserves queued lines. Notices remain with the world below modal backdrops, pause with it and clear on retry or shutdown.
- **Death:** a failed attempt freezes the world and first pans the camera to frame the final presentation floor at the viewport bottom and the sprite frame horizontally at its centre. The pan uses data-configured speed and duration limits with sine easing; an already aligned camera adds no wait. The bird then recoils, falls onto resolved frozen support, squashes on impact and makes a small upward bounce into a seated rest. Void falls retain their configured visible fall above the final floor. Actual lethal object and transient checks record contact provenance; only author-marked red sources trigger `src/scenes/contactFeedback.ts`. Its data-configured camera jolt uses captured world-edge pixels for render-only overscan and restores camera state before the card, retry or shutdown. Controls stay fixed, and reduced motion retains a static border cue without camera movement. `src/scenes/deathCamera.ts` completes the camera pan before animation; the same framing remains through the single death sequence and card capture, with no replay or card-stage relocation. Temporary contact feedback is cancelled before camera scroll and bounds are restored on retry, exit or shutdown, with actors and simulation state preserved. The required `DeathScene` card stays centred horizontally and vertically and holds indefinitely, showing the zone and numbered stage names, current-attempt progress, Last time, Best time and Attempts alongside Stage total, Zone total and Run total. Back to title preserves progress and history; Try again is the safe default and retries the same layout in the same run with fresh object motion. Outside taps, back and Escape cannot close the card. Held input is cleared across transitions, and pause controls stay inert. A four-pixel stage-progress strip at the canvas bottom uses an ink border, a dark-slate track and yellow/amber fill rows; it tracks the current attempt, including backward movement. Death presentation and modal time do not add to active stage time.
- **Stage completion:** [catalogue routing](rules/stageCompletion.ts) saves a nonfinal clear and opens its actual stage preview with Continue, which enters the next stage directly. A destination’s final stage shows its outgoing exchange and statistics before map travel; the final catalogue stage retains its celebration. The preview-first summary has two unboxed three-row columns: Last time, Best time and Attempts on the left; Stage total, Zone total and Run total on the right, with one antagonist statement. [Projection](scenes/runStatsParts.ts) reads cumulative stage/zone time separately from attempt-local values. Run total displays active time only; deaths and completion bookkeeping remain internal. Back, outside taps and held input do not bypass the interstitial, and presentation time does not count as play.

### Screens and UI

- **Scenes:** `BootScene` runs first: it loads everything `public/art/manifest.json` lists and makes an animation of each sprite tag, keyed `<sprite>:<tag>`, with the tag's frames and durations from the sprite's Aseprite export. A tag the sprite's manifest entry lists in `once` plays once and holds its last frame; every other tag loops.
- **Map screen:** six themed destinations each group an ordered catalogue of stage-node ids. The overview shows every regional miniature and name; locked markers use padlocks and unbuilt markers use question marks. Unbuilt stages have no playable plan and cannot be entered. Only manually pressing Continue opens `StageSelectScene`. Its catalogue-ordered cards show actual stage screenshots, standard-size names and smaller stage-number labels. Card capacity derives from the available view width; larger catalogues use pages of full-size cards and open on the latest available stage's page. Hidden cards cannot receive input, and changing pages invalidates held presses. The latest unlocked stage uses the primary style; locked later stages remain visible, grey and disabled. Earlier stages remain replayable. Refused locked cards use the shared disabled-control nudge and label cue, including their screenshot; they never activate or enter keyboard focus. Reduced motion keeps labels steadily red for the cue instead of moving or flashing. Modal-stack changes and shutdown cancel the cue and restore original positions and tints. Closing, back, Escape and outside taps return to the map without selecting a stage. A new navigation press must focus an answer before keyboard activation, so opening input never selects one. Completed stage ids preserve unlocks across replay, and only the configured final apartment stage triggers celebration. The progress format retains catalogue stage ids as additional stages are built. Back to title remains secondary on the left; Continue remains primary on the right and the default map action. Tab selects footer actions, while Left/Right and A/D select unlocked destinations. Returning to the title preserves progress. After a destination's final stage clears, including a replay, the map animates the bird along the drawn route to the next built destination. Input remains locked during travel, the saved position changes on arrival, and arrival does not launch a stage. The final stage retains its celebration.
- **Play view:** the canvas fills `#game` (Phaser's `Scale.EXPAND`), stretched by the most the base resolution takes on both axes, so where `#game` is wider or taller than 2:1 the canvas is too. Each scene's camera shows the game's base-resolution view at the canvas's top, centred across (`src/layout/playView.ts`, `src/scenes/playCamera.ts`), and the canvas's own bars, in the page's ink, fill the rest. Every control stays inside the view across, its drawn edge at least `CONTROL_EDGE` (8) from the edge it is placed against (`src/layout/playView.ts`): the pause button 8 in from the view's top and left; Jump 8 in from the view's right and `CONTROL_BOTTOM` (20) up from the canvas's bottom, with Use 100 above it and 85 in from the view's right, and the move hint level with Jump, as far in from the view's left as Use is from its right; so the bottom controls move into a bar below the game, and none into a bar beside it; the zone draws them in a second camera over the whole canvas, as the pause scene draws the pause button and the dim, and reads a touch's button through the same shift. The move hint (`src/view/moveHint.ts`) is a drawing with no press area: at rest it sits level with Jump, as far in from the view's left as Use is from its right; while a drag moves him, its ring sits where the drag began, held left or right the way he moves, with its knob up to 12 pixels left or right of the ring's centre the way the drag goes, and it returns to rest on release. The [Phaser page-fit adapter](scenes/platform/followFrameTurn.ts) keeps the page no taller than the visible area (the visual viewport, not viewport units, which an installed app can size past the screen) and refits until the sizes settle on every signal that the visible area or the frame's turn may have changed, with a check four times a second while the page is visible for a fit or turn gone stale with no signal.
- **Press areas:** every button's press area is its drawn button grown on every side by a quarter of its shorter side, between 6 and 16 base pixels, and to at least 48 square about its centre (`HIT_RULE` in `src/layout/hitAreas.ts`). Use and Jump instead press within 100 of each centre: a clear circle of radius 63 (`TOUCH_CIRCLE_RADIUS`) and the move hint's radius of 37 beyond it, so a drag, which starts only off the buttons, draws the hint clear of each clear circle. The two are cut along the line midway between their centres, so they meet and never overlap, and Jump's reaches on into the screen's bottom-right corner, from its centre. Where two areas overlap, the button whose centre is nearer the press wins (`pressedArea`).
- **Modal cards:** pause, settings and install steps, restart, stage selection, required dialogue choices, death, updates and paused physical dialogue share the kit's modal input gate and palette-remapped backdrop. `src/view/modalDim.ts` supplies the palette's one-step `darker` map to `modalDimmer` from `@andornaut/game-kit/view/modalDim`, using the shared `MODAL_DIM.rampSteps` value of 3. Each scene adapter owns its cameras and dismissal: modal visuals remain hidden until readback completes, with an opaque ink fallback when capture is unavailable. Owned snapshots and late captures are cleaned up on shutdown. Death sends its unshaded frozen world through the normal painter once; the generic identity bypass is only for genuinely pre-dimmed sources. Settings reuses Pause's cached touch-setting views. The top modal alone accepts Phaser pointers, keyboard, forwarded keys, back events and native page controls, except that Pause also accepts the visible skill HUD targets for details. Every stack change clears held controls and invalidates pending presses, so a release cannot cross into a newly opened card or the world. Outside taps dismiss only closeable cards; required cards remain open. Cards use measured content layout (`src/layout/contentCard.ts`), art's pale `ui-settings-card`, whole-card-centred titles and top-right close faces inset 6px, with full 48px targets excluded from title and body controls. Buttons share standard geometry and primary/secondary styles. Rooms, cutscenes, zone departure and celebration remain full screens.
- **Modal layout:** pause, settings, install steps, restart, dialogue choices and stage selection measure their text and actions through `src/layout/contentCard.ts`. Cards use the shared kit minimum width (half the full logical viewport, bounded by the available view) and 16px outer padding, minimum 16px single-line slots, exported font line pitch for wrapped text, 4px stacked-row gaps and 8px between content groups. Action buttons remain 48px high and share the widest label width plus 32px within each group. Titles reserve symmetric clearance from the full close target and stay centred. All actual modal cards stay centred horizontally and vertically in the logical game viewport. Close faces remain 24px with an unclamped 48px target. Body text and interactive targets start at least 8px below that target; font scale stays fixed.
- **Pause card:** `PauseScene` runs beside `ZoneScene` and draws over it: the pause button at the view's top-left corner, and the card (`src/layout/pauseCard.ts`) that it, P, Escape and back open, with three content-sized buttons sharing the standard height and group spacing, their labels centred: Resume, the primary, then Settings and Back to title. A change of the page frame's turn while the zone plays (the page-frame watcher's `onChange`) opens it too. The card pauses the zone over a dim of it read back from the canvas using the shared modal ramp remap (`src/view/modalDim.ts`), read once for each mix of the two touch settings shown and hidden so the settings card's Move controls and Action buttons rows update the view behind it. Resume, the close X, P, Escape, back and a tap outside it close it; Back to title ends the zone for the start screen. Owned skill HUD targets remain visible beside the card and are excluded from outside dismissal. Tapping one replaces Pause with skill details; closing details resumes gameplay while respecting other pause owners. Tab and the arrows move art's focus ring through Resume, Settings, Back to title and the close X, and Enter and Space press the focused one. While the zone is not in play (under the card, and while `BootScene` loads) the game draws on every Nth display frame, about 60 a second, each draw advancing by the skipped frames' time (the kit's `clock/phaser/capFrameRate`); in play it draws every display frame.
- **Settings card:** the pause card's Settings row opens `SettingsScene` in the pause card's place over the same dim, and the start screen's Settings button over the start screen (`src/layout/settingsCard.ts`): the Move controls and Action buttons rows, the Install row while the game can be installed, and the build label. The scene that opens it passes it the keys and back, and gets it back when it closes. Install shows the browser's install prompt, or the install steps card in the settings card's place. The close X, P, Escape and back close the card on top, back to the scene that opened it; Tab and the arrows move the keyboard's focus and Enter and Space press. Each setting is kept in `localStorage` under its own key (`src/settings/touchControls.ts`). Move controls shows the move hint and Action buttons shows Use and Jump, both on by default; hiding either hides only its drawing, and movement and the button presses still work. A player who hid the old single Touch controls setting starts with both hidden.
- **Skills:** [`skillTuning`](rules/skills.ts) applies only the selected Dash, Double jump or Speedy effect from saved ownership and temporary developer enables. Capability values in `src/data/bird.ts` do not grant ownership. The first eligible skill becomes active; selecting the current skill does nothing, and selecting an ineligible skill is rejected. The first gift selects its skill; later gifts retain the selection. Confirmed Restart clears ownership and selection with progress. All unlocked skills appear in one right-aligned top [HUD row](layout/skillHud.ts). The selected ready glyph is normal, the selected spent/cooling glyph is muted, and both retain their yellow selection bar. Unselected glyphs are muted without a bar. Readiness follows recharge state, not momentary grounded/input eligibility. During play, a tap selects and a hold opens paused [skill details](scenes/SkillDetailScene.ts) without selecting, using `SKILL_GESTURE.holdMilliseconds` (400ms). During Pause, a tap opens details instead. Other modal and dialogue owners block the HUD. Details replace Pause and close directly to gameplay while respecting other input owners. Switching away from Dash stops its active burst without teleporting or refunding cooldown or airborne charges. An actual extra jump starts the attached render-only [air-jump cue](scenes/airJumpCue.ts); its clock advances only with active fixed steps. The active burst also selects the bird’s `dash` body animation; wall or timer exit resumes the normal pose. Active dashes draw procedural wind strokes behind the full sprite frame, following the committed direction and current dash duration through [`DASH_TRAIL`](data/dashTrail.ts). Modal, room, death and pause covers clear the drawing; scene disposal destroys it.
- **Start screen:** The logo uses its loaded frame dimensions and scales proportionally into the space between the nav bar and the unchanged action row. The home page reserves the image's intrinsic height without a fixed brand aspect ratio. Start and Continue use the shared dslate primary face with white text, without a play mark; Restart uses the grey secondary face. With a save, Restart sits on the left and Continue on the right; Continue remains the default keyboard action and first focus target. Their buttons share standard 48px height and matching widths, with an 8px gap when paired. The game always opens on `StartScene` (`src/layout/startScreen.ts`) after loading and startup readiness checks, including with saved progress (Save data): Start opens the unseen opening, then the map with him on the first zone; once progress is saved, Continue (in Start's row, beside Restart) opens the map where he stands (Save data), under a nav bar with Settings, which opens the settings card, and Exit at its right end. Behind them, the opaque 720x360 `start-background` image fills the logical view at native size. Boot loads it from the art manifest's standalone images in development and production; Start draws it directly without launching a zone or capturing the canvas. Exit, and back with no card open, leave through [the page exit handler](platform/pwa/exitApp.ts): an installed app closes its window, and a browser tab goes to the site's home page. Back with the settings card or its install steps open closes them. An installed app whose window a script cannot close ([`appCannotClose`](platform/pwa/appWindow.ts), read in `src/pwa/index.ts` as the page loads: every app but Chrome's on Android and Chrome's and Edge's on desktop, or one whose history holds more than the game's entry) shows no Exit, Settings takes the right end, and back there is the browser's own. Tab and the arrows move art's focus ring through Start, Settings and Exit, as on the pause, settings and install steps cards, and Enter and Space press the focused one (Start with nothing focused).

- **Typography:** [card text](scenes/cardParts.ts) uses native 16px Liberation Sans Regular `font-body` for body text and Liberation Sans Bold `font-title` for headings and action labels. Both draw at scale 1 with exported glyph bearings, kerning and line metrics shared by measurement and drawing. Keep the normal font size and measure/wrap text or enlarge its box. [Action help](view/actionHelp.ts) expands only explicit `{move}`, `{jump}` and `{use}` tokens into canonical labels and existing 40px control icons, with 48px action lines in HTML and gift/detail cards.
- **Input ownership:** [keyboard/touch intent](input/intent.ts) combines movement with eligible [held mouse buttons](input/mouseMovement.ts), keeping opposing directions neutral. HUD, modal and action-button presses cannot claim movement or show its joystick; a separate active movement finger retains its hint. Pause, blur, death and scene transitions clear held controls without reviving them on mouse movement.

### Source layout

- **Phaser boundary:** only `src/scenes/` and `src/main.ts` import Phaser or a scene, enforced by ESLint's `no-restricted-imports`. Logic, layout and data are Phaser-free, so they unit-test without a renderer.
- **View:** `src/view/` picks each sprite's tag and whole-pixel position from the game state, Phaser-free, so the scenes only draw what it picks.
- **Website boundary:** [`src/platform/`](platform/) owns page orientation, PWA and install flows, back navigation, crash UI, DOM progress, browser save adapters and Vite/header tooling. Atlas codecs and packing come from the version-pinned art-kit package. The Phaser host wrapper lives in [`src/scenes/platform/followFrameTurn.ts`](scenes/platform/followFrameTurn.ts) to preserve the renderer import boundary. Game policies and application wrappers stay in their existing directories; pure game-kit imports use the public pinned package. Local copies retain their MIT licence and source revision in `src/platform/NOTICE`.
- **Test helpers:** `src/testing/` is importable only from tests. Game tests own rules, authored data, local platform mechanisms, adapter mappings and lifecycle wiring. Shared-library implementations and public contracts belong to their library suites; consumer tests mock those APIs only to verify real game transformations or lifecycle outcomes.

### Assets and build

- **Shared kit:** `@andornaut/game-kit` is installed from the version-pinned GitHub release tarball in `package.json`, with checksum integrity in `package-lock.json`. The installed package's `SOURCE_COMMIT` identifies its canonical revision. Pure game rules, geometry, clocks, save contracts and stores, and explicit Phaser adapters remain in the kit.
- **Atlas:** a production build packs every PNG `public/art/manifest.json` lists (sprites, tilesets and backdrops) whole into atlas pages, each image's edge pixels repeated 1 px around it, written as lossless WebP with every pixel kept ([atlas adapter](tools/atlas/atlasPlugin.ts)) under `/assets/art/` with a content hash in the name (`src/tools/atlas/`); the atlas manifest that maps each art key and frame to its page and rect is built into the game's code. `BootScene` loads the pages and gives each key a texture that shares its page's source (`src/scenes/atlasArt.ts`), so the page uploads to the GPU once, batches draw from one texture, and code that names a key and its frames works as with the key's own files. Fonts load from dedicated PNG/FNT pairs in both modes. Only their isolated texture sources use linear filtering; sprite atlas sources retain nearest filtering. Standalone manifest images load separately in both modes. The dev server has no atlas and loads each file on its own. Art's files stay as art writes them.
- **Phaser build:** the game runs on WebGL alone, with no sound. A production build bundles Phaser from its source without the namespaces the game does not use, the Canvas renderer or the sound manager (`PHASER_BUILD` in `src/tools/phaserBuild.ts`, built by the [local Phaser build plugin](platform/build/vite/phaserBuildPlugin.ts); its test fails when the game uses something it leaves out), in its own hashed chunk, so an update that changes only game code keeps Phaser's file. The dev server and Vitest load the package's own bundle.
- **Loading:** the initial HTML and lightweight entry show a separate two-pixel themed loading strip at the top through shared kit geometry, the [local DOM progress adapter](platform/progress/dom/progressBar.ts) and the kit's Phaser adapter. Boot reports completed-file progress; startup checks, stage preparation and service-worker installation remain indeterminate. Stage entry yields a paint before synchronous assembly, keeps input and updates disabled, and releases the strip after the first prepared frame. Background caching does not delay play; its indicator follows the shared offline-activity callback without changing registration timing. While any modal input scope is open, `#game[data-modal-open]` raises the Phaser canvas above the DOM strip so all modal scrims and panels cover it. Progress continues updating underneath; closing the final scope restores the ordinary strip layer, and game destruction removes the layer subscription. Preview capture suppresses loading UI.
- **Crash screen:** `src/main.ts` first imports `src/crash/install.ts`, which installs the [local crash screen](platform/crash/crashScreen.ts) in art's palette with the words in `src/data/text.ts`; it pauses the game on the first uncaught error. `?dev=1` adds the error's details. The build label's version and commit come from Vite's `define` in `vite.config.ts`, the commit reading `dev` without git.
- **Security headers:** the build writes `dist/_headers` from `src/headers/securityPolicy.ts`: a Content-Security-Policy per page with its inline blocks hashed, and a year's caching for hashed build output under `/assets/`.

## Game data

### Entities and bindings

- **Game data:** `src/data/types.ts` holds the shapes; gameplay values and player strings live in `src/data/`, with the words the player reads in `text.ts`.
- **Stage element roles:** themes bind shared element roles through `ThemePlan.bindings`. Assembly uses one `bindElement` overlay for repeated backgrounds, local scenery, chunk objects and filled doors. An explicit role without a binding is an error; untagged legacy instances retain their configuration. Bindings select the character and may replace behaviour, lines, parallax, phase or visual skin, merge tuning overrides and set or explicitly clear an introductory scene with `scene: null`. Template placement, dimensions, flags and rooms remain unchanged. `ThemePlan.door` names a required binding role; filled doors use its selected character's dimensions to centre across their slot and stand on its floor. Chunk bounds and seam checks resolve each theme's bindings.
- **Visual skins:** `skin: {art, tileset}` changes presentation while the selected character remains the source of collision, dimensions, hitbox, motion and interaction. A tileset key selects tile art; `null` explicitly selects sprite/image art without falling back to the area's tileset. Sprite art retains its bottom-centred anchor. Collidable skins must preserve the canonical effective hitbox; declared sprite hitboxes are compared after anchoring, tile pieces must match the physical footprint, and skin tiles must exist at the correct tile size. An explicit character change through a binding is configuration, independently of a visual skin.

### Stages

- **Zones:** a zone is played from its `ZonePlan` in tiles (`src/data/types.ts`), converted once to pixels for the rules: areas of terrain and placed instances. Each instance is a character (`src/data/characters.ts`: its art, animations by state, size, words and quirks) on an archetype (`src/data/archetypes.ts`: its collision and default motion, reaction and interaction), resolved once at load into a flat object, an instance's overrides over its character's tuning over its archetype; carried-choice flags place or leave out an instance. Use at a door shows its room (Rooms). Use reaches a door wherever his drawn frame (art's bird frame, placed over his collision box as the zone draws it) intersects the door's rect at all, which is its drawn rect; of two doors under his frame, the one whose centre is nearest his opens (`doorAt` in `src/rules/zone.ts`). His collision box crossing an area's linked edge automatically enters its named target entry, at any height. An unlinked right edge clears the stage, which fades to black and follows its catalogue completion route; the zone walk follows the same links and never presses Use. His box reaching an unlinked left edge (left of `backX`, the first column's right edge) ends the zone without clearing it (`turnedBack`): it fades to black the same way and opens the map with him on that zone, without completion dialogue, statistics or a stage chooser, preserving completion progress and cumulative totals; through `?zone=` it plays the same zone again. Every zone's start, hand-built and every recipe's, sits clear of the first column, and held left from it he reaches that column, nothing in it stopping him (`src/data/zones.test.ts`), and the zone walk counts a try that takes him into it as failed, so neither ends a zone by turning back. A held key's repeats never press it, so a key held from before the zone resumes counts only once pressed again. A zone in `RECIPES` (`src/data/zones.ts`) is assembled from the chunks and themes in `src/data/chunks.ts` for a seed drawn afresh each time he enters it (`src/rules/assemble.ts`): its start chunk, a seeded run of its theme's chunks whose seams join, within its inclusive difficulty band regardless of position, each at most its `maxPerZone` and never one twice in a row, then its finish chunk, the whole within its length, searched with backtracking, with its events and doors in seeded slots (recorded in the plan): a filled door slot places the theme's door at its own size, centred across the slot (half a tile in where the widths differ by an odd count) and standing on its floor, leading to its room. Events are not built yet. Each chunk's contents move to its zone columns, its terrain looks map to the theme's tileset, and the theme's repeated backdrops span the zone; the result is an ordinary `ZonePlan`. Optional `ZoneRecipe.chunks` restricts generated middle chunks to its authored pool; omitting it retains the compatible theme pool. The tests check every chunk against the chunk and seam rules, validate each recipe, and walk each chunk alone (`src/data/chunks.test.ts`, `src/sim/chunkWalk.test.ts`), on small fixtures in `src/testing/chunks.ts` as well as gameplay's chunks. A zone's start is its only checkpoint, and each restart is a new attempt that rolls the objects' random motion afresh from the zone's seed (`?seed=<n>` fixes it).
- **Ordered stages:** each section declares its whole-column `length` range, including only its applicable global stage caps. One or more weighted compatible middle chunks fill that range; limited chunk counts and nonidentical neighbours apply across the stage. Optional `difficultyWeights` multiply chunk weights by grade in flat and ordered recipes; omitted grades keep weight 1 and zero excludes a grade. `areaOrder` retains the generated section sequence and each area's `walkLinks` names its automatic left and right stair destinations. Section changes redraw local art and camera bounds, reset held controls and animation pose, and retain the stage clock and attempt. A retry starts at the stage checkpoint. `src/rules/stageProgress.ts` supplies the same current-attempt fraction to the HUD, death card and diagnostics: ordered sections contribute their playable widths, and the bird's centre supplies local progress. Diagnostic cold starts retain the original stage's progress origin while selecting their own retry checkpoint. Bot input and stall detection reset local state at each section change without reseeding decisions or extending tick and trace budgets. Explicit diagnostic goals remain area-local, including a goal crossed immediately before a stair transition. Optional chunk and recipe `rows` declare matching authored heights; omission retains the library height of 60 rows. `spawnRow` selects an actual opening-cap terrain top without shifting terrain or changing seam rows. A recipe's `stageExit` is local to its final cap and resolves to an area trigger; reaching it uses the existing cleared-stage statistics and Continue flow.

- **Terrain families:** `broad-mesa` and `low-central-crossing` are grade-4 noncombat chunks with ordinary connected routes and explicit required-surface contracts. Normal hostile middle templates use `maxPerZone: 1`; distinct templates in a family remain eligible, and encounter quotas remain recipe data.

### Rooms

- **Rooms:** a door is an instance whose archetype is `door`, with a `room` from `ROOMS` (`src/data/rooms.ts`); the resolver refuses a door without a room and a room on anything else. Use at it holds the zone still and plays the door's `open` tag (its character's `animations.open`, else the tag named `open`) where its art has one, for as long as the tag runs (`src/view/doorOpen.ts`); then `ZoneScene` launches `RoomScene` and pauses, so the pause button hides and P, Escape, back and a frame turn leave the pause card shut. `RoomScene` hides the zone and fills the whole canvas with ink. Ordinary rooms show their backdrop or a PLACEHOLDER frame, animations, cast and centred name. Gift rooms show their configured entry paragraph and portrait with a skill-details card. Ordinary-room Leave stays at the view's top right (`src/layout/roomScreen.ts`), art's `ui-button` with `ui-focus` round it under keyboard focus. Leave, back and Escape close it (`src/pause/roomInput.ts`); Tab and the arrows focus Leave, and Enter and Space press it. The zone resumes with him at the door as he was, the door closed again (its idle tag), with no key or touch held. Gift rooms call [`grantSkill`](save/index.ts) on entry, before acknowledgment, and repeated grants do not stack. Ordinary room entry has no progression effect. Reopening the game mid-room opens the start screen; Continue opens the map with him on that zone. Gift rooms leave through their primary Continue action. The `enter` dialogue supplies the gift paragraph; `shop` remains typed but unbuilt.

- **Door context:** ordinary street and Apartment doors retain their 60x84 footprint and nearest-overlapping-door Use rule. [Facade assembly](rules/roomBuildings.ts) appends mapped 180x180 outdoor buildings after all existing objects and backgrounds, on the door’s 1,1 world plane at depth -3. Their opening aligns at door offset (-60,-96); the full base must have actual solid support. These images add no collision or random draws and preserve prior object indices. Indoor doors retain opaque walls and trim with window exclusions; park/test prototypes are not resized.

### Scenery

- **Parallax:** decorative backdrops can set `parallax: { x, y }` on an instance or a theme backdrop, each factor from 0 (fixed in the view) to 1 (world speed), with both axes at 1 when omitted. Assembly preserves these factors. Outdoor themes may select a reusable [`background catalogue`](data/backgrounds.ts): one fixed weather treatment and independently seeded far/mid sections cover the stage. [`Background assembly`](rules/backgroundSections.ts) appends visual objects after physical objects without consuming terrain randomness or changing existing object indices. Complete authored depth stacks retain their spans and species; generated layers fill only the remaining coverage. Instances with `backdropPlane: 'interior'` use explicit `col/row/cols/rows` as a fixed world rectangle at depth -3.5, between base walls and placed props. [Interior texture phase](view/interiorBackdrop.ts) scrolls inside this two-axis clip, aligned to native tiling at the named `groundAnchor` entry's clamped camera baseline. The quad never moves with parallax or receives outdoor ground-position compensation. Opaque base walls, world-speed props and authored window apertures remain in place. Whole-area layers retain camera scroll factors and their full run width. Explicit repeated chunk layers (`col: 0`, `cols: chunk.cols`) narrower than their area use a world-anchored quad with local texture offsets, clipped to the exact assembled chunk span. Their authored source-height and bottom alignment stay intact. Generated outdoor layers with `backdropExtendBottom` fill an exposed viewport bottom from the native image’s final pixel row, retaining its alpha; indoor planes and ordinary placed scenery do not extend. The renderer updates them before each render, including paused previews and death-camera captures. Placed scenery retains its own art height and bottom anchor while the camera climbs. Noninteractive static sprites with no collision, contact region, quirks or reaction may also use non-default factors, including wait-only animation graphs without entry actions. `ChunkPlan.scenery` appends these instances after existing objects and filled doors, preserving their object indices and motion seeds. They draw behind terrain, cropped to their chunk; camera compensation does not change animation or facing. Other sprites, tiles and placeholders require default factors.

## Save data

Version-10 [progress](save/progress.ts) uses the kit’s versioned save in `localStorage` under `chibis-way-home.save`. It stores the opening acknowledgement, completed stage-node ids, selected stage, seen destination introductions, owned skill ids and one active skill id (or null). Boot loads it after startup readiness. Invalid or older incompatible progress is backed up under `chibis-way-home.save-backup` and resets; a future version is left alone. Cold launch opens Start; saved Continue opens the map. Confirmed Restart clears progress once, including skill ownership and selection.

The separate version-6 [statistics store](save/stats.ts), `chibis-way-home.stats`, retains historical stage/complete-visit bests, whole-playthrough deaths and the active-time ledger:

| Display field | Scope                                         |
| ------------- | --------------------------------------------- |
| Last time     | The attempt that just ended                   |
| Best time     | The fastest successful attempt for that stage |
| Attempts      | The current generated run, including retries  |
| Stage total   | Cumulative active time for the stage ID       |
| Zone total    | Cumulative active time for the zone ID        |
| Run total     | Whole-playthrough active time                 |

Only confirmed Restart clears the three cumulative totals. Start, Continue, fresh map entry, retries and revisits preserve them. Missing stage/zone ledgers initialize once at zero while preserving other saved fields and the known Run total; future active play accumulates normally. New generated runs start with attempt count one; Retry resets only the attempt clock and increments the count. Visit-local summaries remain separate: a zone best requires every catalogue stage in that visit and sums its successful attempt times; incomplete visits cannot set a zone best.

`recordActiveStageStep` counts actual playing steps and records a new death once. Introductory departure counts while play is unpaused; menus, introductory approach/exchange, paused dialogue, cutscenes, death presentation and retry cards do not. Clocks update in memory, checkpoint once per second, and flush on pause, death, exit and page lifecycle events. Where storage is unavailable, saves last for the page session. Settings use separate keys. Developer sessions return zero whole-run totals and suppress normal progress/statistics writes and resets; unknown diagnostic stages do not record real-stage statistics.

## Dev tools

### Browser controls

- **Developer skills:** [developer overrides](dev/mode.ts) are temporary enables in ordinary browser sessions. An unchecked option falls back to saved ownership. Developer sessions read saved ownership and selection but do not write grants, selections, progress resets or stage statistics.
- **Gallery and tuning:** the [asset gallery](gallery/main.ts) at `/art/` lists the current manifest and previews images, animated sprites, tilesets and bitmap fonts using existing exports. The [tuning page](tuningPage/catalogue.ts) at `/tuning/` displays current data as read-only tables; it does not change runtime tuning.

A Dev link below the game opens collapsed controls in regular browser tabs, without requiring a debug URL. Installed apps and fullscreen contexts hide the panel. Hiding it retains the selected controls. The build label remains in Settings, with no version footer in the panel.

Zone and Stage selectors derive from the built catalogue. Load stage sets the selected stage's `zone` parameter and `devSession=1`, preserving existing seed parameters. The invulnerability checkbox records `invulnerable=1` in the URL, retained when loading another stage. Contact hazards and crush deaths are suppressed after the real physics step; falls remain lethal. This protection applies only in regular browser tabs.

`devSession=1` or `invulnerable=1` activates a development session. Loading a stage or changing invulnerability also activates it; merely opening the panel does not. Once active, the central progress and statistics APIs skip loading, corrupt-save backups, writes, clears, statistics mutation and lifecycle flushes. Disabling invulnerability does not restore persistence during that page session. Developer state stays in the URL and page memory, not the save.

Native controls are disabled during boot, modal input scopes and covered play. Modal changes invalidate pending presses, so dismissing a modal requires a fresh press before a panel action can activate.

### Bounded simulations

`npm run simulate -- --help` describes the headless stage runner. Run it only inside the project container. For a small diagnostic run, use `npm run simulate -- --stage street --seed 1 --runs 1 --max-steps 600 --max-retries 0`. Larger batches require coordination with gameplay; this command is not a routine gate. Both this CLI and `src/sim/playabilityCli.ts` refuse an existing `--out` path.

`src/sim/simulate.ts` exposes `prepareStage(layout)` and `simulateStage(tuning, prepared, config)`. `src/sim/report.ts` batches explicit seeds through a caller-supplied preparation function. Layouts and static sensor indices can be reused between policies. The CLI loads art metadata once, assembles each seeded stage once and performs no rendering; optional navigation remains bounded by its explicit prediction-work limits. Its Node-only asset loader is separate from the pure engine and frontend.

Rollouts call the real `stepZone` at `STEP_SECONDS`, including collision, moving platforms, behaviour patterns and explicit retries. Conversations are acknowledged at the runtime proximity and activate their actors; presentation, menu and retry-card waits consume no active time. The bot does not use doors or make narrative choices. Retry retains the assembled layout and uses the real attempt reseeding. Tick and retry limits bound each run and report exhaustion explicitly.

JSON output includes current-attempt and peak progress, completion, death reasons, retries, active seconds, steps and runtime. Per-run timing measures rollout only; aggregate timing includes stage preparation, and total CLI timing also includes asset loading. Timings vary by machine; deterministic gameplay metrics exclude timing. Active seconds count physics ticks across all attempts. Progress uses the same weighted current-position calculation as gameplay across ordered areas. Coverage lists only visited areas and chunks, plus automatic area transitions; prepared but unvisited floors are not covered. `lastAttemptSeconds` reports only the final executed attempt; `successfulAttemptSeconds` appears only after a stage clear and excludes earlier failed attempts. Prediction steps never count toward active time.

Optional `stopAfterStallTicks` (`--stall-limit`) ends a policy with no further directional progress as `policy-stall`, independently of tracing and its event cap. Area changes and retries reset that progress window. Allow for moving-platform cycles and inspect final movement, waiting ticks and planner status before interpreting a stop. Optional `maxWallTimeMs` (`--max-wall-ms`) bounds rollout wall time and reports `wall-budget`. Batch execution counts stage preparation against that same per-stage limit; the batch limit (`--batch-wall-ms`) also bounds preparation and dispatch. Unstarted rollouts appear in `omittedSeeds` and per-seed `omissions`, with reason `batch-wall-budget` or `stage-preparation-wall-budget`. Wall limits depend on machine speed and are incomplete diagnostics, not gameplay failures. A rollout that reaches its wall limit reports `wall-budget`, keeps `fullPass` false and omits `successfulAttemptSeconds`. Use an external container timeout to bound synchronous preparation and individual planning calls as well.

The default `quick` navigation profile retains its existing limits. Explicit CLI `--profile validation` selects planned navigation with a 750-second executed-play budget, three retries, 2,000,000 prediction steps across the run, a 30-second stage wall limit and a ten-minute batch wall limit. Its horizon, candidate count, replan interval and 1,200-tick stall limit remain unchanged. It captures a bounded witness and requires a full pass by default. Explicit overrides may lower these limits, never raise them; the quick profile cannot borrow the larger prediction budget. The profile supplies capacity, not evidence that a stage passed. Catalogue execution and replay must fit the authorized overall budget.

Actual deaths can retain up to sixteen local failed navigation choices across retries of the same run, with nearby dynamic phase context. A fresh stage starts with empty memory. Predicted deaths are not recorded as actual failures, and witness replay uses only its recorded inputs without consulting navigation memory.

Optional `witness: {maxSegments}` (`--witness-segments`) records every executed input with lossless run-length encoding, including retry boundaries. Its explicit segment budget cannot exceed the executed-tick budget. Overflow sets `truncated`; it never becomes a full pass. Witnesses include the exact supplied configuration, resolved seeds, source/data identifiers, actual prepared-layout/tuning hash, final area, tick count and retry count. Supply a nonempty source build identifier when validating.

`fullPass` means an actual whole-stage clear in the final ordered area from its normal checkpoint, with a complete untruncated witness and source identifier. Section goals, cold starts, partial coverage and all budget stops remain non-passes. Batch `validation.fullPass` requires every requested run to pass with none omitted. `--require-full-pass true` requires an explicit witness budget and exits unsuccessfully when that acceptance condition is not met, while preserving the JSON results.

`replayCompletionWitness(tuning, prepared, config, limits, witness)` separately returns `verified` or `mismatch`. It checks stage/tuning context, source/data identifiers, configuration, seeds and segment counts before executing recorded inputs through the same real-step, introduction and retry path as the original run. It has explicit tick and wall budgets and reports its actual executed steps and runtime. Generating a witness does not claim replay verification. Replaying a catalogue stage requires authorization within the overall evaluation budget; it is never an implicit second run.

Every result includes a terminal position/area/chunk and candidate-object snapshot, per-attempt death snapshots and the ordered observed chunk path, independently of trace truncation. Snapshots and trace events record actual `kinematics` fields: `grounded`, `vx`, `vy` and `carryVx`. These identify review locations and policy limits; nearest-object attribution does not establish the cause of a death or prove terrain impossible. Terminal and requested sampled/stall/death events also capture the latest bounded navigation decision: waypoint, selected action, up to eight candidate scores/rejections and predicted endpoints, predicted versus actual progress, replan/cache state and recovery intent. This is the most recent input decision, while the event position is the actual post-step position. Nearby context contains at most four terrain rectangles and four collidable object bounds within half a screen, with actual positions, motion, initial phase, area time and current behaviour/facing/state time. These bounds remain diagnostic candidates, including where lethal body contact uses a narrower silhouette. No full prediction worlds or per-tick dumps are recorded.

Optional `start` selects an existing `{area, entry}` or a collision-box top-left `{area, x, y}`. Bounds and overlaps are checked against actual terrain and initial live objects. Sections initialize the real area's actors and motion at time zero; they are cold starts, not snapshots of earlier play, and retry returns to that same section. No preceding tutorial completion is inferred.

Optional `goal: {area, x}` stops a section at its configured leading-edge threshold in the movement direction with `goal-reached`, independently of stage `cleared`. Goals must be in bounds and ahead of the start. A death at that tick remains a failure. Without a goal the whole stage remains the target; section goals do not count as stage completions.

Optional `seeds` separates `layout`, `motion` and `bot`; each missing value falls back to the existing `seed`. Batch preparation receives the layout seed, rules receive the motion seed and the bot receives its own seed. Results include resolved seeds, the complete supplied configuration, actual starting position and caller-supplied `provenance.build` / `provenance.data` identifiers. Supply exact non-secret source identifiers when comparing data versions. The Node loader adds an SHA-256 identifier of the actual layout, assembled plan and tuning; the CLI also records the Git revision when available, with explicit `--build-id` and `--data-id` overrides. Git identifiers do not describe uncommitted code. Prepared catalogue stages reject mismatched layout seeds and cache only the most recent layout, bounding cache memory.

Optional `trace` requires `maxEvents` and `stallTicks`; `sampleEveryTicks` additionally samples position and input. The run-wide event cap bounds all attempts together and reports dropped events. Death events replace non-death samples when the cap fills. Each event records attempt/local tick, global tick, area, position, input, chunk index and assembly ID where prepared metadata supplies it, death reason and the nearest or overlapping collidable object's position and behaviour. Object attribution is a diagnostic candidate, including after swept contact, not proof of causation. With tracing omitted the runner creates no diagnostic events or object-attribution scans.

Bot inputs expose reaction ticks, look-ahead pixels, jump-hold ticks, error probability, movement direction and jump policy. The reactive policy probes local support, walls and hazards using indexed terrain and current moving-object positions. Optional `jump: "planned"` selects bounded navigation configured by `skill.navigation`: `horizonTicks`, `maxCandidates`, `replanTicks` and `maxPhysicsSteps` (CLI `--plan-horizon`, `--plan-candidates`, `--plan-replan` and `--plan-steps`). Planning uses the real engine; its counters report decisions, candidate rollouts, prediction physics steps and budget exhaustion. The prediction-step budget applies to the whole run, including retries and area transitions; exhaustion reports `prediction-budget` unless the executed tick already cleared the stage or ended in death. A planner with no safe candidate or an exhausted budget has not proved the layout impossible. It does not plan a route, schedule enemy phases or search for takeoffs. The supplied diagnostic settings are not calibrated human skill presets; gameplay owns calibration. Failure by this bot is not evidence that a stage is impossible. Diagnostic defaults enable adaptive holds between `minJumpHoldTicks` and `jumpHoldTicks` for low obstacles, retain longer holds for gaps and hazards, and release after reaching a measured obstacle top. These are local geometric estimates, not skipped physics. `waitForMovers` stops movement for a nearby missing moving landing, resumes on live alignment, and caps waiting with `maxWaitTicks`; no predicted platform position replaces real stepping. Legacy caller skill objects can omit these optional controls.

#### Saved tuning reports

`src/sim/tuningCli.ts` post-processes saved case artifacts and a saved structural playability report without running physics, navigation or replay. Run it in the project container:

```bash
npx tsx src/sim/tuningCli.ts --cases cases.json \
  --structural structural.json --out-prefix reports/tuning
```

The cases manifest is a JSON array of `{ "stage": "stage-id", "path": "stage-artifact.json" }` entries. Artifact paths resolve relative to the manifest. Each artifact contains `run` plus its `sourceCommit`, optional `readinessCommit` and optional `replay` result. Duplicate stage cases are rejected. The output directory must exist; existing `.json`, `.csv` or `.md` outputs are refused without overwriting them.

The JSON report contains stage input counts, recorded chunk-residence tick intervals, revisits, independent failure locations, source/configuration/seeds/replay metadata, zone totals and the existing structural comparisons. CSV and Markdown separate successful-attempt time from all-attempt active time, show input proportions over captured ticks with coverage labels, list slow and revisited chunks, and reuse structural zone comparisons and visited mechanics inventory. A first-attempt full pass requires a full pass with zero deaths and retries plus a complete, untruncated attempt-zero witness whose retry count is zero; replay status remains separate. Residence intervals use recorded centre-based chunk transition ticks, not sampled trace positions. Input counts distinguish direction, reverse direction, no direction, jump presses and held jump ticks. No-direction input does not establish physical waiting, and these artifacts do not measure distance or airtime.

Structural joins require the same source revision, stage, layout seed, area, chunk index and chunk ID. Missing or mismatched joins stay unknown; structural and runtime hashes cover different domains and remain separate. Witness coverage is complete, incomplete or absent, with unknown input ticks reported explicitly. Mechanics present in visited chunks describe available structure, not observed use. These are bot observations and structural proxies, not human difficulty or fun scores; the successful-attempt duration target remains unmeasured by this tool.
